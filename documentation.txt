Exercise-3: Demonstrate Event Handling using JavaScript

Objective:
To understand and implement JavaScript event handling by developing an interactive webpage that demonstrates at least three unique events and performs meaningful actions based on user interaction.

Expected Output The webpage should demonstrate:
- Responsive Design
- Minimum Three Unique Events
- Dynamic User Interaction
- JavaScript Event Handling
- GitHub Repository

Implementation in Canteen Rush:

1. Primary JavaScript Events Demonstrated:
   - onClick Event (Interactive UI Elements): 
     * Checkout Simulation: In `CheckoutPage.tsx`, clicking the 'Pay' button (`onClick={handleCheckout}`) triggers a complex multi-stage asynchronous function that validates wallet balances, initiates simulated API calls with `setTimeout`, and updates the UI state sequentially.
     * Navigation & Modals: Used heavily with React Router (`navigate('/route')`) and state toggles (`setIsUploadOpen(true)`) to provide seamless client-side routing and modal popups without page reloads.
   - onChange Event (Live Data & Controlled Inputs): 
     * Global Search: In `MenuPage.tsx`, the search bar binds to `onChange={(e) => setSearchQuery(e.target.value)}`. This instantly filters the canteen dataset in real-time as the user types, demonstrating live DOM updates.
     * Form Binding: In the Vendor Dashboard, `onChange` binds complex object states (`setNewDish({...newDish, price: e.target.value})`) to keep the React component state perfectly synced with the HTML input values.
   - onSubmit Event (Form Handling & Validation): 
     * Form Interception: Forms across the app (like the Promo Code form) utilize `onSubmit={(e) => { e.preventDefault(); ... }}` to halt the default HTML form submission. This allows the application to handle data via JavaScript, enabling seamless validations and custom API integrations (like Firebase).
   - onMouseEnter / onMouseLeave / Custom Gestures: 
     * Micro-interactions: Integrated with Framer Motion (`whileHover`, `whileTap`) and Tailwind (`hover:scale-105`) to trigger hardware-accelerated CSS animations when a user interacts with buttons and cards.

2. Dynamic User Interaction & Complex Event Handling:
   - Multi-Stage Asynchronous Flows: The payment gateway simulation demonstrates advanced event handling by stacking `setTimeout` functions to mimic network latency. The user interface reacts to these events dynamically, showing loading spinners, authentication requests, and success checkmarks over a 6-second window.
   - Global State Synchronization (Zustand): Events triggered in deeply nested child components seamlessly communicate with parent components. For example, triggering `addToCart()` instantly broadcasts the event to the global store, which dynamically updates the Cart counter badge in the floating navigation bar.

3. Advanced Search and Filtering Functionality:
   - Live Search Event Pipeline: The application implements an efficient filtering algorithm. The `onChange` event of the search input triggers a re-render where the `canteens` array is mapped and filtered based on a case-insensitive `.toLowerCase().includes()` match against the query state.
   - Category Filtering: Interactive category pills ("Fast Food", "Beverages") in the Desktop Landing Page utilize `onClick` events to swap the active dataset mapped to the UI, providing an instantaneous content shift.

4. Form Validation & User Feedback:
   - Real-time Client-Side Validation: Before dispatching data, `onSubmit` events run robust validation logic. For example, the Vendor "Add Dish" form verifies that all mandatory fields are present, and the Promo Code input strictly checks against acceptable strings (e.g., "CHRIST20").
   - Toast Notifications (react-hot-toast): To ensure users are aware of the results of their events, the app fires dynamic, non-blocking toast notifications (e.g., `toast.error('Insufficient Wallet Balance!')` or `toast.success('Order Placed!')`) rather than relying on native browser alerts.

5. Personalized User Interactions:
   - Persistent Dark Mode Toggle: The app listens for a click event on the theme toggle button, which updates the global `darkMode` boolean state. This event simultaneously injects the `dark` class into the root HTML element and persists the user's preference in Local Storage.
   - Campus Location Switching: A custom event flow allows users to select their specific campus (e.g., "Central Campus" vs "Kengeri Campus"). This selection is saved globally and instantly updates textual context across the Dashboard and Landing pages.

6. Responsive & Accessible Design Considerations:
   - Touch-Optimized Event Targets: Recognizing that mouse clicks and touch events behave differently, all interactive elements (buttons, icons, form fields) are padded properly (`p-3`, `min-h-[44px]`) to ensure comfortable interaction on mobile devices.
   - Keyboard Navigation Support: By utilizing native HTML `<button>` and semantic `<form>` wrappers, standard keyboard events (such as pressing 'Enter' to submit a form or using 'Tab' to navigate) are supported natively, fulfilling core web accessibility (a11y) standards.

Lab Exercise 5 & 6: Domain-Based React Application

Objective:
To build a fully functional, domain-based React application (Canteen Rush) by applying core React concepts. This section details how each required concept is technically implemented in the project.

1. Functional Components & JSX:
   - Functional Components: The application abandons older Class components in favor of Modern React Functional Components. For example, `src/pages/MenuPage.tsx` and `src/components/DishCard.tsx` are distinct functions that take `props` as arguments and return UI elements. This promotes code reuse and easier testing.
   - JSX: We use JSX to write HTML-like syntax directly inside TypeScript files. This enables dynamic rendering. For instance, in `CartPage.tsx`, JSX allows us to map over the cart array and conditionally render elements: 
     `{cart.length === 0 ? <p>Cart is empty</p> : cart.map(item => <CartItem key={item.id} data={item} />)}`

2. State Management with useState() Hook & Zustand:
   - useState() Hook: Essential for handling local component changes without reloading the page. In the Vendor Dashboard, we use it to track whether a modal is open: `const [isModalOpen, setIsModalOpen] = useState(false);`. We also use it to hold temporary form data before submission.
   - Global State (Zustand): While `useState` handles local state, we use Zustand to manage the global `cart` state. This avoids "prop drilling" (passing props down 5 levels deep) and allows any component (like the floating Navigation Bar) to instantly know how many items are in the cart.

3. Form Handling & Multiple Input Types:
   - Event Handling: Interactions are driven by React synthetic events. We use `onClick` for buttons (e.g., `<button onClick={handleAddToCart}>`) and `onChange` for text inputs.
   - Form Handling: Forms, such as the one in the Vendor Dashboard for adding a dish, utilize the `onSubmit` event to prevent default browser reloads:
     `<form onSubmit={(e) => { e.preventDefault(); submitData(); }}>`
   - Multiple Input Fields: We manage complex forms using a single state object. When an input changes, we spread the existing state and update only the changed field:
     `onChange={(e) => setNewDish({ ...newDish, name: e.target.value })}`
   - Radio Buttons: Used in the checkout process to let users select their payment method or campus location. The `onChange` event updates the selected radio value in the state.
   - Select Dropdown: The Vendor "Add Dish" form features a `<select>` dropdown to categorize dishes. 
     `<select onChange={(e) => setCategory(e.target.value)}> <option>Fast Food</option> ... </select>`

4. Reusable Components & CSS Styling:
   - Reusable Components: We follow the DRY (Don't Repeat Yourself) principle. The `DishCard` component is written once in `src/components/DishCard.tsx` but is reused dozens of times across the Menu page by passing different data via `props` (`<DishCard dish={item} />`).
   - CSS Styling: We use Tailwind CSS, a utility-first CSS framework. Instead of writing separate `.css` files, we style directly in JSX using class names like `className="flex flex-col p-4 bg-white rounded-2xl shadow-sm hover:shadow-md transition-all"`. This allows for rapid, responsive UI development.

5. CRUD Operations (Create, Read, Update, Delete):
   - Create (Add a new record): The Vendor Dashboard contains a form to create a new menu item. Submitting the form pushes a new dish object into the database/state store.
   - Read (Display all records): The `MenuPage` fetches and maps over the array of canteens and dishes, rendering them dynamically on the screen for the user to view.
   - Update (Modify an existing record): Vendors can click 'Edit' on a dish to change its price or toggle its availability status (e.g., from 'Available' to 'Out of Stock').
   - Delete (Remove a record): Vendors can permanently delete a dish from their menu, and users can delete (remove) items from their cart using a delete button (`onClick={() => removeFromCart(item.id)}`).

6. Bonus: Search Operation (Dynamic Filtering):
   - A real-time search bar is implemented at the top of the Menu Page. We bind a text input to a `searchQuery` state. As the user types (`onChange`), the displayed list of dishes is dynamically filtered using JavaScript's `.filter()` and `.includes()` methods:
     `const filteredDishes = allDishes.filter(dish => dish.name.toLowerCase().includes(searchQuery.toLowerCase()));`

7. Data Storage & Architecture Options:
   - Option 1: Local Storage (Beginner) - *Implemented in this prototype via Zustand Persist*. It stores the user's cart and theme preferences in the browser's Local Storage, meaning data survives page refreshes without needing a backend server.
   - Option 2: JSON Server (Recommended) - The app's data layer is modular. API calls can be easily redirected to a JSON Server to simulate a real REST API (handling GET, POST, PUT, DELETE requests) for educational grading purposes.
   - Option 3: SQLite / MongoDB + Express (Advanced) - Ideal for full-stack deployment. The UI is completely decoupled, making it easy to swap Local Storage with real HTTP requests via `axios` or `fetch` to a Node.js backend.

8. Architectural Benefits Realized:
   - Component-based architecture ensures that complex UI flows (like the Checkout pipeline) are broken down into manageable, independent files.
   - State management using React Hooks makes the UI highly reactive; when data changes, the UI updates instantly without manual DOM manipulation.
   - Strict separation of concerns (UI components vs. state logic vs. data models) vastly improves code maintainability.

9. Mobile Application Conversion Paths (Responsive Design):
   Since the React application is built with a mobile-first responsive design using Tailwind CSS, it can be easily converted into a mobile app:
   - Progressive Web App (PWA): Can run like a mobile app natively in the browser with offline support (Service Workers). Requires no React code changes, just a `manifest.json`.
   - Capacitor (Recommended): Wraps the React web app into a native Android/iOS Webview shell. Students can generate a real APK file and install it on their phones with minimal configuration.
   - React Native (Advanced): Requires rewriting the HTML/Tailwind UI using native mobile components (`<View>`, `<Text>`). Best suited for a dedicated mobile development phase.

Lab 7: Node.js File System (FS) Module

Objective:
Develop a Node.js program to demonstrate the File System (FS) module by securely writing domain-specific details (Canteen Orders) using both synchronous and asynchronous APIs.

Implementation in Canteen Rush:
To follow industry-standard best practices, the File System module was integrated into a secure Client-Server Architecture:

1. Frontend Client UI (React): 
   Running in the user's web browser, the React application intercepts the Checkout 'Pay' event and triggers an asynchronous HTTP POST request (`fetch('/api/lab7/save-order')`) to the backend with the user's order details.
   
2. Backend Server Runtime (Node.js):
   The backend Express server (`server.js`) handles the request and interacts directly with the host Operating System.
   - Synchronous API: During server startup, `fs.existsSync` and `fs.mkdirSync` are used to synchronously verify and create a secure `server_data` directory.
   - Asynchronous API: The REST endpoint utilizes `fs/promises` (`appendFile`) to securely write the incoming order data into `server_data/canteen_orders.txt` without blocking the main event loop.

Browser Sandbox Isolation:
The File System (FS) module cannot be used directly inside React. Because React runs in the browser, direct access to the local storage/machine files is blocked to prevent critical security exploits. Web browsers run client-side code in a highly restricted sandbox to protect the host machine.

Operating System Integration:
Node.js executes directly on the system level, permitting API actions like file reading/writing. This architecture keeps file system operations securely isolated on the server.
